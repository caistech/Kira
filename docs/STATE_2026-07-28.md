## THE TASK LOOP IS CONNECTED (2026-07-28, late)

`owner → Kira → orchestrator → task → approval → send → callback → Kira → owner`

Both ends had worked for a while and **nothing joined them** — `getSwarmCoordinator()` only ever
returned `LocalSwarmStub`, so nothing in Kira had ever called `/v1/dispatch`. Two working systems
and a contract, no adapter. Now built on both sides:

- **Out:** `lib/kira/swarm/orchestrator-adapter.ts` — same `SwarmCoordinator` interface, over HTTP.
  Degrades into something Kira can SAY rather than silence; a failed approval is never reported as
  sent.
- **In:** `app/api/kira/webhooks/task-events` — the return leg. Separate secret from the outbound
  one (outbound proves Kira to the orchestrator; this proves the orchestrator to Kira, so a leaked

  whichever brain did the work.

**Harness: `scripts/test-task-loop.mjs` — 10/10 passing against production.** It asserts the
negatives too (no secret, wrong secret, forged callback, unsigned poll all refused), because a
happy-path-only test would have passed through both of today's silent failures. Verified the
completion actually landed in `kira_tasks`, not merely that it returned 200.

## 3. The billing model — DECIDED, not built

Operator's wording, verbatim: **"owed but unbilled til 30th is the correct wording."** The month is
owed from day one and simply not invoiced until the period closes. If the owner cancels before that
bill falls due, the in-progress month is **waived as a gift** — no proration, no argument
("thanks for trying us out and off you go"). Because the waiver is permanent rather than a
month-one offer, the true line is stronger than any trial: *you are never billed for the month you
are in*.

**The code does not do this.** `app/api/checkout/route.ts` passes `trialDays: 30, cardAtSignup:
true` — a free trial then **advance** billing. Same date, same $999, inverted contract: the day-30
charge buys days 30–60 instead of paying for days 0–30, and a cancellation on day 45 has already
been paid for. Under the intended model this **under-bills by one month per customer** — safe
direction, real money.

**To wire it:** `@caistech/subscription-billing` cannot express arrears (`DynamicPriceLineItem`
exposes only `interval`, no `usage_type`), so it needs a metered price added — and **LaunchReady is
the other consumer**. Metered invoices at period close by construction and
`cancel(prorate: false, invoice_now: false)` discards the accrued period, which *is* the waiver.
Two traps: dropping `trialDays` without switching to metered charges $999 at checkout immediately;
and unreported usage invoices $0 silently, so the report needs an assertion rather than a hope.

**The waiver must be a tested code path, not a policy we intend to honour.** An invoice landing
after a 66-year-old has cancelled is the worst thing that can happen to this ICP's trust, and he
tells his broker — who is the distribution channel.

**Shipped meanwhile (PR #61, squashed to `286d66c7`):** the `/plan` card no longer contradicts
itself. Four "30 days free" strings now follow the same `billingLive` switch as the price line and
fine print; live-mode wording is byte-identical, so flipping `STRIPE_LIVE_MODE` restores it with no
edit. **Do not write the arrears promise onto the page before the mechanism exists** — that
recreates the exact lie the page was just cured of.

**One line for a cold session:** *the copy is honest and the billing is not — build the metered
arrears path with a tested waiver before promising it on the page.*

# Addendum — arrears billing is BUILT (2026-07-28, later still)

The model from §3 above now exists as code. **Not yet exercised against real Stripe** — see the
verification gap at the end, which is a genuine one.

## What changed

**`@caistech/subscription-billing` v0.2.0** (published, and Kira is on it):
`ensureBillingMeter` · `ensureMeteredPrice` · `reportPeriodOwed` · `cancelWithWaiver`, plus an
`arrears: true` line-item shape for `createSubscriptionCheckoutSession`. Passing `trialDays` with it
now **throws** rather than quietly choosing one of two contradictory offers. 12 new tests, 40 total.

**One correction to the plan.** It could not be a flag on `DynamicPriceLineItem` as scoped: Checkout's
inline `price_data.recurring` accepts only `interval`/`interval_count` — no `usage_type`, no `meter` —
so an arrears price must EXIST before the session does. Hence `ensureMeteredPrice`, keyed on a
deterministic `lookup_key` so a per-customer band doesn't mint a new Price object every checkout.
Legacy usage records are also gone in Stripe ≥18, so this is Billing Meters, and aggregation is `sum`
rather than `last` to stay compilable on the package's stripe ≥17 peer floor.

**A second correction: LaunchReady is not a consumer.** Nothing in the portfolio depends on this
package except Kira — LaunchReady still runs its own `app/api/stripe/*` fork, which is pre-existing
un-migrated debt rather than something this change orphaned. "Reconcile LaunchReady" was therefore
not required; the change is additive in any case.

**Kira:** `lib/billing/arrears.ts` (when a period counts as owed + the waiver), the reporting hook on
the adapter's `apply`, `POST /api/billing/cancel`, `CancelPlanButton` in Settings, and the migration
`20260728180000_billing_periods_reported.sql` — **applied to prod and verified** (table + column
present, RLS on).

## The three failure modes it is built around

- **Reported twice → billed double.** Stripe's meter `identifier` only dedupes over "at least 24
  hours", nowhere near a billing period, so the durable record is ours: a unique
  `(subscription, period_end)` claim taken BEFORE the send and released if the send fails.
- **Never reported → invoices $0, silently, in our favour** — against a subscription that looks
  healthy on every screen. So the report THROWS on failure, which inside the webhook becomes a 500,
  which releases the reducer's claim, which makes Stripe retry.
- **Cancelled and billed anyway.** The waiver is `cancelWithWaiver` (`invoice_now: false` +
  `prorate: false`), a named function rather than two options set correctly at a call site.

## Two things this uncovered that were already broken

- **`introductions.status` was never advanced.** Nothing in the codebase ever wrote `trialing` or
  `paying`, so the introducer board's two headline tiles counted zero however many owners were being
  billed — an advisor deciding whether referring people is worth it was reading a frozen board. Now
  synced from the subscription (fail-soft), and the "Free month" label is gone, since arrears has no
  such state.
- **The pre-charge notice would have gone quiet.** `trial_reminder_sent_at` was a once-ever stamp, correct
  when there was one charge to warn about. Under arrears every month ends in a charge, so it is now
  keyed per period (`users.charge_notice_period_end`) and the email says "for the month just gone".

billed for the month you are in.* Beta strings are untouched and still true. This was not optional:
