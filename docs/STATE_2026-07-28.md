## THE TASK LOOP IS CONNECTED (2026-07-28, late)

`owner → Kira → orchestrator → task → approval → send → callback → Kira → owner`

Both ends had worked for a while and **nothing joined them** — `getSwarmCoordinator()` only ever
returned `LocalSwarmStub`, so nothing in Kira had ever called `/v1/dispatch`. Two working systems
and a contract, no adapter. Now built on both sides:

- **Out:** `lib/kira/swarm/orchestrator-adapter.ts` — same `SwarmCoordinator` interface, over HTTP.
  Degrades into something Kira can SAY rather than silence; a failed approval is never reported as
  sent.
- **In:** `app/api/kira/webhooks/task-events` — the return leg. Separate secret from the outbound
  one (outbound proves Kira to the orchestrator; this proves the orchestrator to Kira, so a leaked
  env cannot forge completions). Mirrors into `kira_tasks` so one table serves the owner's surfaces
  whichever brain did the work.
- **Orchestrator side:** `GET /v1/tasks/:id` (poll) + `notifyCaller` on send AND failure, fail-soft.

**Harness: `scripts/test-task-loop.mjs` — 10/10 passing against production.** It asserts the
negatives too (no secret, wrong secret, forged callback, unsigned poll all refused), because a
happy-path-only test would have passed through both of today's silent failures. Verified the
completion actually landed in `kira_tasks`, not merely that it returned 200.

⚠️ **`KIRA_SWARM_ADAPTER` is deliberately NOT set — production still uses the local stub.** The
seam is proven; flipping which brain answers a real owner is a separate, conscious decision.

## DECIDED — Gareth's memory-governance layer stays OUT of Kira's live path (operator, 2026-07-28)

The standing question ("what would Gareth's memory harness do to the product — enhance, degrade,
neutral, and does the advisor care?") is now **answered and agreed on all four points.** Do not
re-open it without new evidence; the reasoning, not just the verdict, is below because the verdict
alone reads as a rejection of a partner and it is not one.

**What we know, evidenced:** Gareth owns *swarm · memory harness · agent builder*
(`docs/GARETH_SHAH_INTEGRATION_SEAMS.md`, Seam 2 hands the working↔semantic boundary to him and
Shah to draw). Shah's confirmed Mnemo surface is `search` with `includeSources`, `x-workspace-id`
isolation, and `getmnemo-migrate` with machine-readable reports — provenance, isolation, lifecycle.
Operator's 2026-07-24 call was *build, lane TBD*.

**Against what Kira has:** a live loop, per-user RLS in **our own** Supabase, HMAC-verified
webhooks, distil-on-post-call, recall-at-connect, 5/5 on the memory-loop probe, Genome
classification and export on top.

**The verdict, by part:**

1. **ENHANCE — provenance on recall, and only that.** We have *when* something was captured; we do
   not have *which conversation, in whose words*. This matters for one reason that connects to
   money: the Genome is a handover document a buyer's accountant reads cold. *"The pricing rule is
   X"* is a claim a buyer discounts. *"The owner stated on 3 March that the pricing rule is X"* is
   evidence. That is the difference between shortening due diligence and not.
2. **DEGRADE — write ownership.** Seam 2 #7 is load-bearing: one writer per path, or memories
   double and conflict. Kira's loop works *now*, and the scar tissue is direct — the convai saga
   where the agent called its memory tools and always got nothing took two production incidents to
   find, because every response was a healthy 200. A third party in that path multiplies the
   failure surface of the one thing that is green.
3. **NEUTRAL — isolation and audit are not a gap we have.** Per-user RLS in our own substrate is
   *stronger* than a workspace header on someone else's, and `DATA_STANDARD` **S1** says own the
   substrate for authoritative data. The Genome is drifting toward authoritative — it is the
   handover artefact. Moving it into Mnemo would be a **downgrade dressed as governance**, and this
   is a citable constraint on any design Gareth/Shah propose, not a preference.

**Does the advisor care?** She is risking her licence and her client relationship, so what she
actually asks is: *if I refer Bob and it tells him something wrong, whose problem is it? Bob's
competitor is also your client — can anything cross? If Bob sells or dies, does his data come out?
Can I see what it told him?* Isolation, export and provenance answer three; a disclaimer answers the
fourth. **A governance layer is one route to those answers; a written trust artefact plus Genome
provenance is a cheaper route to the same yes** — a day, versus a Tier-1 build. Commercially
governance is a **hygiene factor** for her: it can lose the deal, it does not win it. Building
hygiene infrastructure pre-Gate-2 is the over-build failure `THIN_MVP_RUBRIC` exists to catch.

**The four agreed actions:**

1. **Do not adopt the harness into Kira's live path.** The seam interface already exists, so the
   option is held at zero cost — that is what the seam is for.
2. **Build the one piece that pays** — source provenance on Genome entries, in our own Supabase.
   **Measured, not assumed (2026-07-28): 54 of 61 active memories ALREADY carry
   `source_conversation_id`.** The post-call distil writes it (it calls `handleSaveMemory` without
   an `identity`, so the canonical conversation binding resolves and populates the column). The 7
   without are mid-call `save_memory` tool writes through our uid path
   (`lib/kira/uid-tools.ts`), where the package hard-codes `id: null` on the identity branch
   because uid mode historically had no conversation id — `platformIdentity: true` now supplies
   one, so that gap is closable.
   **So the real gap was never capture — it was SURFACING.** The provenance existed and no screen,
   and crucially no export, ever showed it.
3. **Answer the advisor with a written artefact, not an architecture** — the four questions,
   plainly. Operator's placement call: **in the FAQs *and* as an artefact on the advisor page**, so
   it is in front of her rather than found.
4. **Keep the governance layer as its own opportunity.** Gareth reselling a CoE layer to his clients
   is a real lane-1 shape and the lane question stands — but it must not be justified by Kira's
   needs, because Kira does not have them. A build justified by a need that does not exist is how
   you end up with infrastructure and no distributor.

**One line for a cold session:** *take the provenance, decline the write path, and do not let a
partner's roadmap become our dependency while our own loop is the thing that is green.*
