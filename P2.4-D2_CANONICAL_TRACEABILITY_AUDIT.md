## 0. Executive Verdict

**Kira is converging on the canonical model, but unevenly, and the convergence is incomplete at three well-defined boundaries.**

The canonical separation (Organisation = enduring anchor, Person = provenance) is *correctly implemented* at the schema layer for the majority of tables with an organisation_id column, and *partly correct* in application code. It is *not complete* for:

1. **The live bridge resolver** — `get_organisation_id_from_user()` still returns the user's own UUID when asked "what is this user's organisation?". The 1:1 bridge assumption (`organisations.id = users.id`) is **false in live data** (35 orgs vs 4 persons vs 6 legacy users; all 14 memberships have `person_id ≠ organisation_id`). Every insert that relies on that trigger stamps `organisation_id = user_id`, i.e. a person UUID in an organisation column.
2. **Memory/task/draft surfaces** — `kira_memory`, `kira_tasks`, `kira_knowledge_chunks`, `client_profiles`, `pubguard_scans` write/read by `user_id` as the ownership selector; `kira_tasks` and `kira_knowledge_chunks` have **no organisation_id column at all**.
3. **The legacy `users` table still being the identity bridge** — acceptor/auth routing runs through `users.id`; canonical identity (`persons` + `auth_credentials` + `organisation_memberships`) exists but is not yet the single authority.

The exercise is **not** mechanical string-replacement, and the audit evidence confirms the codebase is being reasoned about in canonical terms (every rebound boundary resolves a Person→Organisation via membership before applying an org filter). The remaining work is bounded and enumerable.

- DROPPED `get_organisation_id_from_user()` — **not present in live pg_proc** (the §2.1/bridge threat below is retired; audit first-draft overstated it)

## 6. Convergence Assessment (the question asked)

The audit confirms Kira is **converging architecturally, not mechanically**:

- Ownership-vs-provenance reasoning is explicit in code and tests (P2.4-A/B/D artifacts read as canonical-model reasoning, not string substitution).
- The canonical chain resolver exists and is dogfooded in 33 files; new rebound code consistently resolves Person→Organisation via membership before filtering by `organisation_id` — exactly the invariant the model requires.
- The schema layer is mostly correct: 30+ tables org-anchored; several (`kira_agents`, `conversations`, `business_valuations`) fully or structurally canonical.

The three convergence gaps are *defined and bounded*:

1. **Residual fallback branches in DB+Bridging function** (§2.2) — the direct `users.id = auth_user_id` fallback inside `resolve_organisational_context()`/`resolve_organisation_id_from_auth()`/`link_or_create_app_user()` and the dead `resolve_user_id_from_organisation()`. The insert-trigger bridge is already retired; this is the remaining SQL-level bridge surface.
2. **Memory/task/draft ownership read-path** (§3.2) — `kira_memory`, `kira_tasks`, `kira_knowledge_chunks`, `client_profiles`, `pubguard_scans` and the kira convai/recall/chat/webhook cluster need the org-anchor write path (the P2.4-A LEGACY backlog).
3. **Legacy `users` identity bridge retirement** (§5) — end-state decision for `users` (billing subject vs fully retired).

Plus one data-gap item: **79 `genome_facts` rows with NULL organisation_id** (41 unmapped-real-owner + 38 sentinel) — org-invisible under RLS (§4).

**Verdict:** NOT a mechanical sweep — the architecture is being rebased onto the canonical model, and the most dangerous bridge surface (org-sync insert triggers) is already retired live. Residual legacy is concentrated in the memory/task/draft cluster, two bridging functions + fallback branches, and the 79-row data gap. These are the next remediation candidates.
